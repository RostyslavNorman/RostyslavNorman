## Featured Projects

<details open>
<summary><b>Resalekh Place — Streetwear E-Commerce Platform</b></summary>

<br/>

A production e-commerce platform for a streetwear resale business: catalogue, faceted search, cart and checkout flow, and a full admin panel for inventory and content management. Built Ukrainian-first with internationalised routing.

| | |
|:---|:---|
| **Stack** | Next.js 15 · React · TypeScript · Tailwind CSS · shadcn/ui · Drizzle ORM · Supabase (Postgres, Auth, Storage) · Vercel |
| **Scale** | Multi-brand catalogue keyed by manufacturer article code, with a dedicated `product_content` table for localised SEO copy |
| **Performance** | Server Components for catalogue rendering, image optimisation, URL-synced filter state so every result set is shareable and cacheable |
| **Security** | Supabase Auth with row-level security policies, server-side validation on all mutations, admin routes behind role checks |
| **Impact** | Replaced a manual Instagram-DM sales process with a self-serve storefront and an admin panel the owner operates without developer help |
| **Repository** |[Live Demo](https://https://resalekhplace.com)|

Designed the architecture up front — PRD, decision log, and a ten-milestone build plan — before writing feature code, with the admin panel deliberately placed on the critical path so the product was operable from the first release rather than developer-dependent. The filter sidebar mirrors Nike's faceted-search UX, with every facet serialised into the URL so state survives refreshes, back-navigation, and sharing. Also involved real cross-browser engineering, including diagnosing and fixing a Safari-specific `aspect-ratio` bug on flex children.

</details>

<details>
<summary><b>National Gallery Route-Finder — Graph Pathfinding Application</b></summary>

<br/>

A JavaFX desktop application that computes optimal walking routes between artworks in London's National Gallery, comparing multiple traversal strategies over a real floor-plan graph.

| | |
|:---|:---|
| **Stack** | Java · JavaFX · XML data layer · JUnit |
| **Scale** | Complete gallery graph in `gallery_data.xml` — rooms, doorways, artworks, and weighted connections |
| **Performance** | Dijkstra for shortest path, BFS/DFS for comparison, plus a "most interesting route" variant that maximises artwork exposure under a distance budget |
| **Security** | Input validation and defensive parsing of the external XML data source |
| **Impact** | Visualises algorithm choice as a concrete, human-readable difference in route quality |
| **Repository** | [View Source](https://github.com/RostyslavNorman/National-Gallery-Route-Finder) |

The interesting problem was rendering: routes had to be drawn over a raster floor plan without crossing walls, solved with a pixel-level BFS that treats the image itself as the traversable grid. The result is a route line that follows corridors rather than cutting through them — algorithmically correct paths that also look correct.

</details>

<details>
<summary><b>Autumn Leaves Identification System — Image Processing & Union-Find</b></summary>

<br/>

A JavaFX application that segments leaves from scanned images, classifies them, and animates an optimised tour between detected specimens.

| | |
|:---|:---|
| **Stack** | Java · JavaFX · Custom Disjoint-Set (Union-Find) · Image processing |
| **Scale** | Per-pixel connected-component analysis across full-resolution leaf scans |
| **Performance** | Union-Find with path compression for near-linear component labelling; nearest-neighbour TSP heuristic for the tour animation |
| **Security** | Bounds-checked pixel access and safe handling of malformed image input |
| **Impact** | Demonstrates classical data structures solving a real computer-vision segmentation task without external CV libraries |
| **Repository** | [View Source](https://github.com/RostyslavNorman/Autumn-Leaves-Identification-Vision-System) |

Built the disjoint-set structure from scratch rather than importing one, which made the union-by-rank and path-compression trade-offs measurable in the application's own runtime rather than theoretical.

</details>
