## Featured Projects

<details>
<summary><b>Resalekh Place — Production E-Commerce Platform</b></summary>

<br />

A full production storefront for a Ukrainian reseller of authentic branded footwear and apparel.
Built and operated solo: inventory pipeline, catalog, cart, checkout, payments, order lifecycle,
admin CMS, image pipeline and observability.

| | |
| :--- | :--- |
| **Stack** | Next.js 16 (App Router) · React 19 · TypeScript (strict) · Tailwind v4 · Drizzle ORM · PostgreSQL · Supabase · Zod · sharp · Sentry |
| **Scale** | ~730 inventory rows · ~340 article codes · ~25 brands · multi-SKU size matrix |
| **Performance** | Server Components by default · ISR with on-demand revalidation · WebP pipeline with 400/800/1600 responsive variants · mobile-first budgets |
| **Security** | Server-authoritative pricing · `SELECT … FOR UPDATE` stock locks with deterministic lock ordering · RLS enabled on every table · service-role isolation · MFA-gated admin |
| **Impact** | Live commercial platform generating real revenue; zero client-trusted monetary values |
| **Repository** | [RostyslavNorman/resalekh-place](https://github.com/RostyslavNorman/resalekh-place) |

The hard problem was not the storefront — it was **integrity**. Inventory lives in a read-only Google
Sheet the client owns and edits daily; editorial content lives in Postgres. The storefront is the join
of the two, which means the sync layer must normalize inconsistent human input (NBSP-separated prices,
Cyrillic size labels, unmapped brand spellings) without ever failing a request or writing back to the
source.

Checkout is fully unauthenticated, so the client sends only `{skuCode, qty}` — **every price is
recomputed server-side** and the invoice amount is frozen at creation, never re-derived from a payment
callback. No order row exists until the payment provider confirms; the pre-payment snapshot lives in a
separate table and is garbage-collected. Stock is taken under row locks in a deterministic order to
make concurrent checkouts deadlock-free.

</details>

<details>
<summary><b>AI Content Backfill Pipeline</b></summary>

<br />

An LLM-driven content generation system that eliminated the launch bottleneck for the platform above:
hand-authoring editorial copy for hundreds of catalog items.

| | |
| :--- | :--- |
| **Stack** | TypeScript · Claude API · Node.js · Drizzle ORM · PostgreSQL · sitemap crawling |
| **Scale** | 285 of 343 article codes matched — **83% automated coverage** |
| **Performance** | Cached sitemap discovery (24h, ~5 MB) · batched inference · idempotent, resumable runs |
| **Security** | Deterministic code-based matching with double verification · robots.txt compliance · no search-endpoint scraping |
| **Impact** | Reduced weeks of manual data entry to a single reviewable batch |
| **Repository** | [Part of resalekh-place](https://github.com/RostyslavNorman/resalekh-place) |

Naive approaches to this problem fail in two ways: fuzzy name matching produces wrong products, and
copying source prose produces duplicate content that is penalised in search. This pipeline avoids both.

Matching is **structural, never semantic** — article codes are normalized to `[A-Z0-9]` on both sides,
and a URL-slug hit alone is never trusted; the fetched page's model field must independently confirm
the match or the row is skipped. Generation consumes only the **structured specification table**
(materials, colour, season, closure) and produces original copy, with the prompt explicitly forbidding
invented materials or technologies and branching by product category.

Critically, **nothing publishes itself**. Every generated row lands hidden, tagged with provenance and
a null review timestamp, and enters a dedicated admin review queue. The pipeline only considers items
with neither description nor images, so it can never overwrite human work and is safe to re-run after
an interrupted batch.

</details>

<details>
<summary><b>Image Processing Pipeline</b></summary>

<br />

A content-addressed image ingestion pipeline solving a subtle rendering defect: supplier photos arrive
with inconsistent backgrounds, and anything short of pure white reads as a visible rectangle against
the product plate.

| | |
| :--- | :--- |
| **Stack** | Node.js · sharp · Supabase Storage · SHA-256 content addressing |
| **Scale** | Full catalog imagery · 3 responsive variants per asset · backfill tooling for existing objects |
| **Performance** | WebP conversion · 400/800/1600 resize ladder · CDN-served · deduplication by content hash |
| **Security** | Server-only service-role access · MIME validation with automatic unpublish on failure |
| **Impact** | Consistent, professional product presentation across every surface and both themes |
| **Repository** | [Part of resalekh-place](https://github.com/RostyslavNorman/resalekh-place) |

The white-point correction is **multiplicative rather than a threshold clamp** — a linear transform
that maps the measured background to 255 while leaving black at black and shifting mid-tones by roughly
one percent. It only fires when all four image corners agree within six levels and none is darker than
232, so photographs with real scenes, gradients or intentionally coloured backdrops pass through
untouched, and alpha is flattened onto white first.

Storage keys hash the **original** bytes, not the processed output, so re-uploading the same source
overwrites in place instead of orphaning objects. Correction is disabled for hero banners and brand
logos, which are not rendered on a plate. Failures are swallowed by design: the correction is cosmetic
and must never fail an upload.

</details>

<details>
<summary><b>Payment & Order Integrity Layer</b></summary>

<br />

The transactional core of the platform: two settlement modes, both cleared online, with a strict
guarantee that no order exists until money has actually moved.

| | |
| :--- | :--- |
| **Stack** | TypeScript · Next.js Server Actions · Drizzle ORM · PostgreSQL · monobank hosted invoices · Nova Poshta API · Telegram Bot API |
| **Scale** | Full payment, fixed prepayment with cash-on-delivery remainder, full order lifecycle |
| **Performance** | Row-level locks with deterministic ordering · webhook and redirect-side reconciliation · 2h snapshot GC |
| **Security** | Server-recomputed totals · invoice amount fixed at creation · callback amounts never trusted · frozen order snapshots |
| **Impact** | Zero client-trusted monetary values across the entire purchase flow |
| **Repository** | [Part of resalekh-place](https://github.com/RostyslavNorman/resalekh-place) |

The design decision that matters here is **when an order comes into existence**. Creating an order
before payment means reconciling abandoned checkouts and phantom stock reservations forever; creating
it after means the checkout state must survive a redirect to a third-party payment host. This layer
takes the second path: the snapshot is persisted separately, stock is not reserved, and only a
confirmed payment materializes the order — reserving stock, denormalizing line items, and firing
notifications.

Order items are **denormalized at write time** — name, brand, size and price are snapshotted — so order
history stays truthful even after the catalog changes underneath it. Totals are frozen and never
re-priced after payment, and cancellation restores stock as a terminal transition.

</details>

<details>
<summary><b>Inventory Sync Engine</b></summary>

<br />

A read-only, normalization-heavy sync layer between a client-owned Google Sheet and PostgreSQL,
designed to be resilient to messy human input and hard serverless timeouts.

| | |
| :--- | :--- |
| **Stack** | TypeScript · Google Sheets API · Drizzle ORM · PostgreSQL · Apps Script webhook · GitHub Actions cron |
| **Scale** | ~730 rows · ~340 articles · per-SKU pricing · full and incremental sync paths |
| **Performance** | Chunked batches of ~100 rows to stay inside a 10s serverless function limit · 5s per-row webhook debounce |
| **Security** | Token-gated sync endpoints · strictly read-only against the source sheet |
| **Impact** | The client keeps working in a familiar spreadsheet; the site stays consistent automatically |
| **Repository** | [Part of resalekh-place](https://github.com/RostyslavNorman/resalekh-place) |

The governing constraint is that **the source is not ours to change** — no new columns, no write-back,
no schema negotiation. Everything ugly must be absorbed on our side: non-breaking-space thousands
separators in prices, Cyrillic characters mixed into Latin size labels, brand spellings that vary by
row, and range labels that must survive as-is rather than being parsed into numbers.

Unknown values are **logged and reported, never fatal** — an unmapped brand produces a warning and a
telemetry event, not a failed sync, because a single bad cell must not take down the catalog. A full
sync would blow the platform's function timeout as one request, so it is chunked with awaits between
batches, and an `onEdit` webhook handles single-row updates with debouncing for bulk edits.

</details>
